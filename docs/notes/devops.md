## Network / DNS — image build (both debian_qcow2 scripts)

- **Rule:** Both images unify on **ifupdown + standard `/etc/network/`**, configured by the `netui` dialog TUI (`bin/netui`, shipped to `/usr/local/bin/netui`). DHCP by default; static is set via `sudo netui` (incl. its "Capture DHCP lease -> static" action). NetworkManager and ceni are NOT used. The cloud-init image (`debian_qcow2.sh`) forces cloud-init to render via the **eni** renderer (`system_info: network: renderers: ["eni"]`). The no-cloud-init image removes cloud-init and ships `/etc/network/interfaces` = `lo` + `source /etc/network/interfaces.d/*` with a netui-managed `interfaces.d/eth0` (DHCP default).
- **netui design (stateless, in-memory):** `interfaces.d/<iface>` IS the single source of truth. netui parses it into memory on edit and renders back on SAVE. No shadow data model, no `/etc/network/netui/` directory, no `.bak` files. Unknown options (`bridge_ports`, `vlan_raw_device`, `hwaddress`, ...), in-stanza comments, and trailing stanzas (e.g. `inet6`) are preserved VERBATIM. Apply uses an ephemeral `/tmp/netui-rollback-<iface>` + systemd-run timer (cancelled on user confirm). UI is `dialog` (not `whiptail`), matching `deskui` conventions (`--no-ok --cancel-label "Back"`, `DLG()` wrapper).
- **DNS:** `systemd-resolved` is removed; **resolvconf** manages `/etc/resolv.conf` (ifupdown `dns-*` options + dhcpcd). `/etc/resolv.conf` MUST be linked to `/run/resolvconf/resolv.conf` via `virt-customize --link` — NOT `--run-command 'ln -sf'`, which libguestfs reverts because it swaps `/etc/resolv.conf` for appliance networking during `--run-command`/`--install` and restores the original afterwards. Verified on live VMs: Proxmox cloud-init nameservers AND DHCP nameservers both land in `/etc/resolv.conf`.
- **Context:** Rewritten from a `whiptail` TUI that kept a redundant shadow model in `/etc/network/netui/<iface>/main.conf` + `*.lines`. That double bookkeeping drifted from the real file on manual edits and was a non-standard invention. Supersedes the earlier rule "cloud-init image uses the NetworkManager renderer" (commit b199fa3). The user chose to unify both images on ifupdown+netui+resolvconf. cloud-init's eni renderer places `dns-nameservers` on `lo`, but resolvconf (unlike the systemd-resolved if-up hook, which exempts lo) DOES capture lo-placed DNS, so no relocation fixup is needed. See [[1781049600-cloud-init-eni-resolvconf-dns-debian]].
- **Updated:** 2026-06-15

## Network — eth0 DHCP default when cloud-init has no datasource (both cloud-init images)

- **Rule:** `debian_qcow2-cloud-init.sh` AND `debian_qcow2-cloud-init-selkies.sh` **pre-seed cloud-init's own eni render path** `/etc/network/interfaces.d/50-cloud-init` with a plain IPv4 DHCP stanza (`auto eth0` / `iface eth0 inet dhcp`) at build time. When a datasource IS present, cloud-init **OVERWRITES** this exact file with the datasource's config (verified: a static IP is applied cleanly, no leftover DHCP). When no datasource is attached (ds-identify disables cloud-init) the DHCP default stays and ifupdown brings up eth0; dhcpcd handles IPv6 via RA. SINGLE file → no duplicate `eth0` stanza, no extra service.
- **Context:** Debian `ds-identify` DISABLES cloud-init when no datasource is found (default policy `notfound=disabled`); genericcloud ships no static eth0, so a VM booted WITHOUT a cloud-init drive rendered nothing and eth0 stayed `qdisc noop state DOWN`. Two rejected alternatives (both live-tested): (1) force cloud-init on via `ds-identify` `notfound=enabled` → ~240s EC2 IMDS probing (169.254.169.254) + cloud-init 25.1.4 hardcodes `dhcp4+dhcp6` in `generate_fallback_config()`, whose `iface eth0 inet6 dhcp` line fails (`No DHCPv6 client software found!`; Debian 13 dropped isc-dhcp-client, image uses dhcpcd) → failed `networking.service`; (2) a separate static `interfaces.d/eth0` (or a `netcfg-fallback` oneshot) → cloud-init writes a SEPARATE `50-cloud-init`, so WITH a datasource both files are sourced → duplicate/conflicting eth0 stanza (live test: eth0 got BOTH a datasource static IP and a DHCP lease, default route via the wrong one). Pre-seeding `50-cloud-init` itself sidesteps both — it is the very file cloud-init overwrites. NOTE: netui owns `interfaces.d/eth0` (a DIFFERENT file); in the cloud-init images the network authority is cloud-init/datasource, not netui — configuring eth0 via `sudo netui` here while `50-cloud-init` exists would create two stanzas. Details: [[1781322000-cloud-init-no-datasource-eth0-dhcp-fallback]].
- **Updated:** 2026-06-15

## Selkies image — externalized payloads (services + start scripts)

- **Rule:** The Selkies builder (`debian_qcow2-cloud-init-selkies.sh`) keeps its service units and start scripts as real files in the repo under `linux-debian/selkies/` instead of inline heredocs. The builder stays a SINGLE downloadable file: payloads are fetched at build time from `LINUX4U_REPO` (repo raw root `raw.githubusercontent.com/nchekwa/linux4u/${LINUX4U_REF}`, ref = `LINUX4U_REF`, default `main`); the `linux-debian/selkies/` subpath is appended inside the fetch helpers. `curl` runs on the **HOST** (to `mktemp -d` BUILD_TMP, cleaned by an `EXIT` trap), then files are injected with `virt-customize --copy-in` — NEVER `--run-command 'wget/curl'` inside the guest, which would hit the appliance DNS-swap (see Network/DNS rule). `netui` is fetched the same way (`${LINUX4U_REPO}/bin/netui` → `--copy-in /usr/local/bin`). Templated payloads use the `.tpl` suffix and are rendered with `envsubst` using a **restricted variable list** (e.g. `envsubst '${DESKTOP_USER}'`), so build-time vars are filled while runtime `${HOME}`/`${DISPLAY}` stay literal. Secrets (`SELKIES_PASSWORD`, `VNC_PASSWORD`) stay as host env vars and are never committed. Payloads SHARED with the other builders (`quick_upgrade.sh`, `99-eni.cfg`, `50-cloud-init`) now live in `linux-debian/base/` and are pulled via a `fetch_base` helper — see the base/ rule below; only desktop-specific payloads stay in `linux-debian/selkies/`. A live login banner `99-motd-update.tpl` → `/etc/update-motd.d/99-motd-update` (pam_motd runs `/etc/update-motd.d/*` per login on Debian genericcloud → `/run/motd.dynamic`; the script resolves the VM IP fresh via `hostname -I` and prints Selkies URL/login + VNC ssh-tunnel + change-password/restart commands). **Default creds** (overridable via env): Selkies web basic-auth = `selkies`/`321selkies`, VNC = password-only `321vnc`. The system/desktop user (`DESKTOP_USER`, default `user`) is left at its existing default and is NOT tied to these. `DESKTOP_USER` has **passwordless sudo** (`/etc/sudoers.d/<user>`: `NOPASSWD:ALL`, mode 0440) so admin commands (MOTD restarts, `/opt/scripts`) never prompt. Requires `gettext-base` (envsubst) on the host.
- **Context:** Replaced 6 escaped heredocs (`\${DISPLAY}`, `\"`) that were unlintable, and moved the `netui` fetch from in-guest `wget` (hardcoded `refs/heads/main`) to host `curl` + `--copy-in` (now ref-pinned via `LINUX4U_REF`). Details: [[1781308332-selkies-payload-externalization]].
- **Updated:** 2026-06-15

## Build — shared payloads in linux-debian/base/

- **Rule:** Payloads duplicated across builders live in `linux-debian/base/` and are fetched at build time via a `fetch_base <name> <out>` helper (HOST `curl` from `${LINUX4U_REPO}/linux-debian/base/$1` → `${BUILD_TMP}` → `virt-customize --copy-in`), so every builder stays a SINGLE downloadable file. Current base payloads: `download_scripts.sh` + `quick_upgrade.sh` (→ `/opt/scripts`, ALL three builders), and `99-eni.cfg` (→ `/etc/cloud/cloud.cfg.d`) + `50-cloud-init` (→ `/etc/network/interfaces.d`) (the two cloud-init builders). `netui` is fetched the same host-`curl`+`--copy-in` way (`${LINUX4U_REPO}/bin/netui` → `/usr/local/bin`) in ALL three builders. Every builder defines `LINUX4U_REF` (default `main`) + `LINUX4U_REPO` and a `BUILD_TMP=$(mktemp -d)` cleaned by an `EXIT` trap. NEVER `--run-command 'wget/curl'` inside the guest (appliance DNS-swap).
- **Context:** DRYs the per-builder inline heredocs (`/opt/scripts/*.sh`, `99-eni.cfg`, `50-cloud-init`) and unifies netui delivery on the selkies host-`curl`+`--copy-in` pattern (the cloud-init/no-cloud-init builders previously used in-guest `wget` hardcoded to `refs/heads/main`). Supersedes the earlier "`99-eni.cfg` stays inline" note. selkies' own desktop-specific payloads stay in `linux-debian/selkies/` (fetched via `fetch_payload`). Test builds can point `LINUX4U_REPO` at a `file://` checkout. Verified on a live `file://` build (payloads land + eth0 DHCP without a datasource).

## Selkies image — transport is WebSocket (Selkies 2.x), WebRTC dropped

- **Rule:** The Selkies image streams over **WebSocket only**. WebRTC is **removed as a deployment option** — not kept as a fallback, not selectable at build time. This requires **Selkies 2.x**, which has no upstream release: the builder pins the untagged commit `be53b2c39670ccd1432fe50ebcd6d0ade72ce80a` (2026-08-22). `--mode=websockets` AND `--enable_dual_mode=false` are both passed: `enable_dual_mode` defaults to `true` upstream and would let the web client switch back to WebRTC, reintroducing the exact failure this change removes.
- **Context:** The old image baked `releases/latest` = **v1.6.2, which is WebRTC-only** (no `--mode` flag exists in its 48 args). WebRTC media is UDP/SRTP, and a Cloudflare orange-cloud proxy carries only TCP on a fixed port list — so signalling succeeded over HTTPS and the desktop never painted. User decision (2026-09-07): "zastępujemy obraz webrtc.. nie chce tego gówna" — replace in place, no `STREAM_STACK` switch, no dual-stack image. The untagged-commit risk was explicitly accepted ("akceptuje po wersji"). `be53b2c` is the last commit before `7c40254` pinned `pixelflux~=2.1.0`/`pcmflux~=2.1.0`, which do not exist on PyPI (only 2.0.0) — HEAD of `main` therefore fails to install. Rejected alternatives: coturn over TCP/TLS 443 on a separate gray-cloud hostname (keeps WebRTC, adds a public service + credential lifecycle to operate) and KasmVNC (released and WebSocket-native, but has **no audio**, and this image treats the audio pipeline as mandatory — see the streaming-defaults rule). Details: [[1788739200-selkies-2x-websocket-migration]].
- **Updated:** 2026-09-07

## deskui — runtime resolution change lives under the Selkies menu

- **Rule:** `bin/deskui` can change the stream resolution at runtime from a **fixed list** (`1920x1080` / `2560x1440` / `3840x2160`, no free-text entry). It lives under the **selkies** submenu, not a separate "desktop" one — that is what the user is configuring, even though the value is physically the Xvfb `-screen` geometry in `/opt/selkies/start-desktop.sh`. It follows the existing deskui pattern: `sed` the wrapper script, verify the write by reading it back, then restart. Because `xfce-session.service` owns the display and `selkies`/`x11vnc` only attach with `Requires=` (**not** `PartOf=`, so systemd will NOT cascade), the restart must name **all three units explicitly** or the clients keep pointing at a dead `:99`. The action is destructive (open windows lost; `start-desktop.sh` wipes `~/.config/xfce4` on every start; clients must reconnect), so it is gated behind a `--defaultno --yesno` warning listing those consequences. The **main menu** uses `--ok-label "Select"` + `--cancel-label "Exit"`; submenus keep `--no-ok` + `"Back"`.
- **Context:** User request 2026-09-08. A first pass put this in its own top-level `desktop` submenu; the user rejected that as "bez sensu" — from the operator's point of view resolution is a Selkies setting, so a third service entry was noise. Free-text entry was also declined in favour of a fixed list. The menu header shows the current value (`Login: x   Resolution: y`) so no extra screen is needed to read it. Verified by rendering every dialog in a pty (all fit 24x80) and by round-tripping the `sed`/`grep -oP "(?<=^RES=')[^']+"` pair against a real rendered `start-desktop.sh`. See the streaming-defaults rule for why this is a CEILING, not the working resolution.
- **Updated:** 2026-09-08

## Selkies image — native runtime libraries + build-time smoke test

- **Rule:** The Selkies venv's compiled extensions need OS libraries that **no pip metadata mentions** — they are ELF `NEEDED` entries, findable only with `objdump -p`/`ldd`. The builder installs `libxkbcommon0`, `libpulse0` plus `libva2`, `libva-drm2`, `libva-x11-2`, `libgbm1`, `libdrm2`, `libpixman-1-0`, `libice6`, `libsm6`, `libxext6` (the `libva*` group via `--run-command 'apt-get install --no-install-recommends'`, because `virt-customize --install` always pulls Recommends and `libva-drm2` Recommends `va-driver-all` → ~19.5 MB of GPU drivers). **`libva*` is required even though the VM is GPU-less and the encoder is software x264:** the `pixelflux` manylinux wheel bundles ffmpeg+x264 under `pixelflux.libs/` but deliberately does NOT bundle `libva`, and its bundled `libavutil`/`libavcodec`/`libavfilter` are built WITH VA-API, so those SONAMEs resolve **unconditionally at dlopen time, before any encoder is chosen**. A linker dependency is not a functional one. Every build now runs a **smoke test inside the image**: an `ldd` sweep over every `*.so*` in the venv (catches any unbundled library, including ones a future wheel bump adds) followed by `import pixelflux, pcmflux, selkies`. The build FAILS on a broken install.
- **Context:** Live VM 2026-09-08 (commit `1572c93`): the image built cleanly, all three services were `active`, HTTPS returned 200 and input worked — but **no video ever rendered**, browser stuck on "Waiting for stream". Cause: `import pixelflux` raised `ImportError: libva-drm.so.2: cannot open shared object file`. Selkies downgrades that to a single startup `WARNING`, then reports only `Cannot start capture: the pixelflux library failed to import` on each connect, so `journalctl -n 50` after the fact shows the effect with no cause. Adding the three `libva` packages fixed it instantly with no other change. The bug survived pre-commit testing because the import was verified on a **build host that already had libva** — hence the in-image smoke test, which is the actual regression guard. `build success != image works`. Details: [[1788825600-selkies-libva-pixelflux-import]].
- **Updated:** 2026-09-08

## Selkies image — audio (PulseAudio) applies to EVERY desktop user

- **Rule:** System-mode PulseAudio (`pulseaudio-system.service`, daemon drops to the `pulse` user, plus a `module-null-sink` virtual speaker) is installed **unconditionally**, and `usermod -aG pulse-access` targets `${DESKTOP_USER}` — not hardcoded `root`. `selkies.service` always gets `After=pulseaudio-system.service` + `Environment=PULSE_SERVER=unix:/run/pulse/native`. System mode is used because **no** user here gets a logind session: neither `selkies.service` nor `xfce-session.service` sets `PAMName=login`, so `/run/user/<uid>` never exists and a per-user daemon is impossible for a normal user exactly as it is for root. `XDG_RUNTIME_DIR` falls back to **`/run/selkies`** (this image's `RuntimeDirectory=selkies`, owned by the desktop user), never `/tmp`.
- **Context:** All of this previously lived inside `if [ "$DESKTOP_USER" = "root" ]`, so the **default** image (`DESKTOP_USER=user`) shipped with no audio server at all while `libpulse0` was installed unconditionally — client library present, no server. Every client connect then looped a `pulsectl` stack trace and the session was silent. The fix had been scoped to the condition it was debugged under rather than to its cause; root's inability to run a per-user daemon explains why root needs *system* mode, not why a normal user would need nothing. The old `XDG_RUNTIME_DIR=/tmp` fallback actively masked this: `/tmp` is root-owned `1777`, so PulseAudio correctly refused it (`XDG_RUNTIME_DIR (/tmp) is not owned by us, but by uid 0`), turning "no runtime dir" into a misleading "connection refused". **Superseded claim:** the comment "Selkies' audio pipeline is MANDATORY (its failure aborts the video stream)" was true for 1.x/WebRTC (one GstPipeline for both paths) and is **false since the 2.x/WebSocket migration** — audio and video are independent pipelines; verified on a live VM that video streams fine with PulseAudio completely dead. Do not diagnose "Waiting for stream" as an audio problem.
- **Updated:** 2026-09-08

## Selkies image — 2.x install is built on the HOST, injected offline

- **Rule:** Selkies 2.x is assembled on the **HOST** and injected with `virt-customize --copy-in`; the guest runs **no** `pip`/`npm`/`git`/`curl` against the network. Three host-built artifacts: (1) a **wheelhouse** (`pip download` of the pinned source tarball + deps) installed in-guest with `pip install --no-index --find-links=`, (2) the **web client** (`npm ci && npm run build` in `addons/selkies-web-core`) shipped as `dist/` and passed via `--web_root=`, (3) nothing else. **`node`/`npm` are NOT installed in the final image** — they are build tooling only. Selkies lives in a venv at `/opt/selkies/venv`, not `pip --break-system-packages`.
- **Context:** Extends the existing "NEVER `--run-command 'wget/curl'` inside the guest" rule (see Network/DNS). The old builder was an exception: it ran `curl | tar` inside the guest, placed deliberately BEFORE the DNS block so appliance DNS still worked. That exception does **not** scale to `pip install` + `npm install` (memory/time in the libguestfs appliance, and `addons/selkies-web-core` ships no lockfile at `be53b2c`, so `npm install` is non-reproducible). **Verified 2026-09-07:** at `be53b2c` the ENTIRE dependency set resolves to prebuilt wheels (`pip download --only-binary=:all:` succeeds) — nothing compiles. The `xkbcommon` **Python package is NOT a dependency at this commit** (it was at the older `348bc4f`); `input_handler.py:88` loads the C library directly via `ctypes.CDLL("libxkbcommon.so.0")`, so the guest needs the `libxkbcommon0` **apt** package, not a built wheel. Wheels are still Python-ABI-specific (`cp313` etc.), so the wheelhouse MUST be produced on a host whose Python matches the target: **Debian 13 = Python 3.13, Debian 12 = Python 3.11**. Because of this the builder supports **Debian 13 only** and fails fast on `12` (user decision 2026-09-07). Do NOT strip `av`/`cryptography`/`pylibsrtp` the way linuxserver.io's Dockerfile does — at `be53b2c` `src/selkies/__main__.py` imports `webrtc_mode` at **module level**, so removing them breaks startup even in websockets mode.

## Selkies image — streaming defaults (framerate, bitrate, resize)

- **Rule:** The Selkies builder bakes in explicit encoder defaults instead of inheriting upstream's. Build vars (all overridable via env, exported for `envsubst`): `SELKIES_MAX_RES` (default **`2560x1440`**, raised from `1920x1080` on 2026-09-08), `SELKIES_FRAMERATE` (30), `SELKIES_VIDEO_BITRATE` (8000 kbps), `SELKIES_AUDIO_BITRATE` (64000 bps). `SELKIES_RES` is kept only as a backwards-compat alias for `SELKIES_MAX_RES`. **`SELKIES_MAX_RES` is a CEILING, not the working resolution:** `start-selkies.sh` runs `--enable_resize=true` and Selkies resizes the framebuffer DOWN to the client window via xrandr — Xvfb's RANDR `maximum` is pinned by the initial `-screen` geometry and **cannot be raised at runtime**, so a client asking for MORE gets a scaled image plus an `RRAddOutputMode BadMatch` burst on every connect (`RRCreateMode` succeeds, attaching the oversized mode fails, leaving an orphan mode behind in the X server). The default was raised to `2560x1440` because a common HiDPI laptop (2880x1800 panel at default scaling) asks for ~2880x1580 and was being clamped. Cost is RAM only — `W*H*4` bytes, ~14 MB vs ~33 MB at 4K — and a higher ceiling costs no bitrate/CPU at smaller windows since Selkies only scales DOWN. `--congestion_control=true` is set deliberately because it is the ONE encoder setting the web client cannot override (the runtime JSON at `/tmp/selkies_config.json` only overlays framerate/video_bitrate/audio_bitrate/enable_resize/encoder onto args); `SELKIES_JSON_CONFIG` stays at its `/tmp` default so a bad client-side choice is cleared on reboot. `--encoder=h264enc` is the 2.x spelling (allowed: `h264enc`, `openh264enc`, `h264enc-striped`, `jpeg`); the old `x264enc` is silently aliased to it at `settings.py:1201`, but the alias is undocumented so the real name is used.
- **Context:** A fresh image streamed 1080p60 CBR, pegging a core at ~112% on an idle desktop. The previous `--enable_resize=false` was justified by a comment claiming "Xvfb has a FIXED geometry (no RANDR modes to add)" — **verified false**: `xrandr --newmode/--addmode/--output --mode` all succeed on Xvfb, only `maximum` is fixed. Supersedes the single `SELKIES_RES` geometry var. `xfce-session.service` gained `RuntimeDirectory=selkies` + `RuntimeDirectoryPreserve=yes` so `start-desktop.sh` can publish the session D-Bus address to `/run/selkies/dbus.env` for `selkies.service` (without it `xfconf-query` fails and DPI/cursor scaling never applies); `Preserve=yes` stops a desktop restart deleting the file under a running Selkies. The `SELKIES_TURN_*` vars and the `GST_PLUGIN_*`/`GST_REGISTRY_1_0` workaround documented here previously are **GONE** as of 2026-09-07: 2.x has no GStreamer (`pixelflux`/`pcmflux` instead) and `turn_*` is never read in websockets mode — see the WebSocket rule above. Details: [[1788480000-selkies-streaming-defaults-xvfb-randr]].
- **Updated:** 2026-09-07
